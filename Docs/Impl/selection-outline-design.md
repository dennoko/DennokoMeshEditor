# 選択アウトライン抑制の再設計案

作成日: 2026-09-18。設計・調査のみ。実装変更および Unity 上の描画検証は未実施。
基準環境は本プロジェクトの Unity 2022.3.22f1。Unity 6 は別途実機検証する。

## 1. 結論

**第一候補は、Unity 全体の Selection Outline 設定を変更せず、公開 API の `EditorUtility.SetSelectedRenderState` で編集対象だけを抑制する方式。採用前に、NDMF を含む実際の描画経路でアウトラインが消えることを確認する。**

判定は「以前に抑制したか」から切り離し、**現在、有効な編集セッションがあり、その Renderer が編集対象か**に統一する。終了イベントは即時反映に使い、正しさをイベントの到着順や Scene ビューの描画に依存させない。

この方式を選ぶ最大の理由は、変更する状態が実行中メモリにしか無いことである。Unity が異常終了しても次の起動に何も持ち越されないため、クラッシュ時の後始末そのものが要らなくなる（5 節）。永続設定を書き換える現行方式では、ここが原理的に埋まらない。

公開 API で必要な輪郭を消せない環境では、グローバル設定の自動変更へ暗黙に戻さない。まず自動抑制を無効にして通常のアウトラインを許容する。全対応環境での自動抑制が必須なら、後述の「編集対象と Unity の選択を分離する方式」を選ぶ。この判断を描画結果の推測や実行時の自動切替に任せない。

## 2. 調査で確認できたことと、未確認のこと

- 現行 `SelectionOutline.cs` は内部 API `AnnotationUtility.showSelectionOutline` と固定の EditorPrefs キーを使用する。復元失敗時にキーは残すが、通常の終了時に再試行を予約しない。
- `EditSession.End()` は `_active == null` なら終了する。復元待ちと編集セッションの寿命が分離されていない。
- 選択解除と対象消失の終了判定は `OnSceneGui()` にある。Scene ビューが描画されなければ終了が遅れる。
- `Suppress()` の二重抑制ガードは退避キーの有無で判定しており、キーが所有権の表明も兼ねている。復元が成功するまでキーは消えないので、内部 API を解決できない Unity では起動時の復元と新規の抑制が同時に止まる。
- `EditorApplication.update` の購読はセッションのインスタンスに紐づき、`End` で外れる。セッションが無い状態で解除待ちを進める駆動源が現状は無く、Inspector の `OnEnable` が代役になっている。
- Renderer 単位の抑制も既に存在するが、`Refresh()`、`DisposeTargets()` に分散している。プロキシの参照を置き換える際、以前に抑制した生存中のプロキシを必ず復元する管理にはなっていない。

既存コメントの「SetSelectedRenderState はワイヤーフレームにしか効かない」は、普遍的な API 仕様として扱わない。公式資料では `Hidden` は選択ハイライトとワイヤーフレームの両方を非表示にする指定である。ただし、その説明だけでは今回問題になる NDMF 使用時の輪郭まで抑制できるとは保証できない。[SetSelectedRenderState](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/EditorUtility.SetSelectedRenderState.html)、[EditorSelectedRenderState](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/EditorSelectedRenderState.html)

Unity 2022.3 の公開 C# ソースでは、SceneView は選択から集めた Renderer の ID とアウトライン設定を描画処理に渡す。最終処理はネイティブ側であり、C# 側に Renderer 状態の検査がないことだけでは「Hidden が効かない」と断定できない。6000.0 ブランチも同様の呼び出し構造である。各ブランチの参照であり、2022.3.22f1 と全 Unity 6 パッチの一致を保証する調査ではない。[SceneView 2022.3](https://github.com/Unity-Technologies/UnityCsReference/blob/2022.3/Editor/Mono/SceneView/SceneView.cs)、[Handles 2022.3](https://github.com/Unity-Technologies/UnityCsReference/blob/2022.3/Editor/Mono/Handles.cs)、[SceneView 6000.0](https://github.com/Unity-Technologies/UnityCsReference/blob/6000.0/Editor/Mono/SceneView/SceneView.cs)

## 3. 方式の比較

| 方式 | 長所 | 問題・採用判断 |
| --- | --- | --- |
| Renderer 単位の公開 API | 全体設定に触れず、対象が限定される。既存 UI を維持できる | 第一候補。実描画での有効性と解除を検証する必要がある |
| 編集対象と Unity の選択を分離 | 選択アウトラインの対象自体をなくせる。設定の復元が不要 | 自動抑制必須で公開 API が使えない場合の候補。Inspector と選択操作の設計変更が必要 |
| 全体設定をセッション中ずっと OFF | 現行 UI を保ちやすい | 異常終了すると永続設定が OFF のまま確定し、ツール側から復旧できない（5 節）。復元、複数起動、外部変更との競合も抱える。新設計の標準方式にはしない |
| 描画前に全体設定を OFF、描画後に復元 | 変更時間は短くなる | 前後の別コールバックは一つの try/finally ではない。例外・描画中断・複数ビューで取り残す余地があるため不採用 |
| 非編集中は無条件に ON | 判定が短い | ユーザーが意図して OFF にしている設定を破壊するため不採用 |
| Unity 内部の選択キャッシュを空にする、描画処理をパッチする | 描画のみを直接制御できる可能性 | バージョン依存と他ツールとの競合が大きく、単純化にならないため不採用 |

EditorPrefs はプロジェクト固有の保存先ではない。固定キーに「退避値がある」ことを「この Unity が抑制中」とみなす設計は避ける。プロジェクトごとにキーを変えても、変更する設定そのものが共有なら競合の解決にはならない。[EditorPrefs](https://docs.unity3d.com/ja/2020.3/ScriptReference/EditorPrefs.html)

## 4. 抑制する条件を一つにする

セッションには開始要求とは別に `Running` 状態を設ける。初期化成功後にだけ Running にし、終了時は後始末より先に解除する。

```text
CanContinueEditing(session) =
    session が存在し Running
    AND コンポーネントが Unity の null 判定で生存
    AND その GameObject の Scene が有効かつロード済み
    AND その GameObject が現在の選択に含まれる
    AND Play Mode 中でも移行中でもない
    AND 終了・リロード処理中でない

ShouldSuppress(renderer) =
    CanContinueEditing(session)
    AND renderer が生存
    AND renderer が現在の編集対象の元 Renderer または対応プロキシ
```

`Running` は開始処理が完全に終わってから立てる。`Begin` は自分で `Selection.activeGameObject` を書き換えるため、その最中に `Selection.selectionChanged` が届く。**Running でない間に届いた選択変更は無視し、終了として扱わない。** 共通条件をそのまま終了判定へ流用すると、開始途中のセッションが自分の選択操作で終了する。終了処理中に届いた分も同様に無視し、`End` は再入しても安全にする。

コンポーネントの enabled / GameObject の activeInHierarchy を条件に加えるかは、編集機能自体の仕様と揃える。アウトライン専用に異なる終了規則を追加しない。破棄済み Unity Object の判定に C# の参照 null 判定だけを使わない。

Scene ビューのフォーカス、マウス位置、Inspector の表示、頂点選択の有無、ドラッグ中かどうかは条件に含めない。Inspector へ移動しても編集は続き、頂点未選択でも編集前の輪郭は邪魔になるためである。

プロキシ未生成や一時的な NDMF 再構築はセッション終了としない。元 Renderer は対象に残し、取得できるプロキシだけ追加する。変形計算が元 Renderer にフォールバックしても、描画中のプロキシが存在するなら抑制対象から落とさない。

## 5. 一か所で対象集合を整合させる

`SelectionVisualController` に選択表示の書き込みを集約し、メッシュの生成・破棄処理から独立させる。単一セッションなので参照カウントや汎用ロック機構は不要。

保持するものは「自分が非表示を試み、まだ解除していない Renderer の集合」。この集合は**後始末の台帳**であり、抑制するかを決める根拠にはしない。

```text
Reconcile():
    desired = CanContinueEditing ? 現在の元 Renderer とプロキシの集合 : 空集合

    台帳にあり desired にない Renderer ごとに:
        破棄済みなら台帳から除去
        生存中なら通常状態へ戻す
        成功したものだけ台帳から除去

    desired 内の Renderer ごとに:
        台帳に登録してから Hidden を適用
        失敗しても台帳を残し、他の Renderer の処理を続ける
```

プロキシ A → B の交換では、生存中の A を解除してから B を抑制する。元 Renderer とプロキシが同じなら集合で重複を除く。メッシュ読み出しや BakeMesh の成功を表示の解除条件にしない。

選択変更で Renderer 状態が初期化される可能性があるため、加入時だけの書き込みに限定しない。選択変更時に再適用し、低頻度の update（既存の 0.1 秒程度）でも対象を整合させる。常時の全シーン走査はしない。変更または再適用が必要なときだけ再描画する。

NDMF のプロキシ登録が描画直前に行われるため、update だけでは新プロキシの初回描画に間に合わない可能性がある。必要なら `ProxyRegistry.Report` で対応する一体だけを同じコントローラーに通知して適用する。描画タイミングへの依存は抑制の即応に限定し、終了・解除は update だけでも進むようにする。無条件に描画コールバックを追加せず、ちらつきの実測で必要性を判断する。

### 駆動と購読

コントローラーの `EditorApplication.update` は静的に 1 本だけ持ち、「Running なセッションがある、または台帳が空でない」間だけ購読する。両方が消えたら外す。現行のようにセッションのインスタンスへぶら下げると `End` で購読も外れ、「セッションなしでも解除待ちを再試行する」が成立しない。Inspector の `OnEnable` を駆動源の代役にしない。

ドメインリロード後は `[InitializeOnLoadMethod]` で SessionState の台帳を読み、空でなければ編集を再開しないまま購読だけ張り直す。台帳が空なら何も購読せず、常駐コストを残さない。

### ライフサイクル

| 契機 | 処理 |
| --- | --- |
| 開始成功 | Running にして Reconcile |
| `Selection.selectionChanged` | Running でなければ何もしない。Running なら共通条件を評価し、不成立なら終了、成立なら表示を再適用 |
| `EditorApplication.update` | セッションの有効性と台帳を整合。セッションなしでも解除待ちがあれば再試行 |
| 明示的終了・対象消失 | Running を解除し、desired を空にしてからメッシュ等を後始末 |
| Play Mode 移行・シーンを閉じる・終了・リロード前 | 新規抑制を止め、解除を試みる。繰り返し呼んでも安全にする |
| シーンを開く・Prefab モードの出入り | 選択が変わるため共通条件で終了する。Scene の妥当性でも判定し、選択イベントが届かない経路を塞ぐ |
| Inspector の OnEnable / OnDisable | 表示所有者にしない。複数 Inspector の生成・破棄で編集状態を動かさない |

終了処理は、まず `_active` からセッションを切り離して再入を防ぐ。選択表示の解除、Tools.hidden の復元、メッシュ後始末、プレビュー通知は、一つの失敗で残り全部が飛ばない構造にする。少なくとも選択表示の台帳は Cleanup の例外で破棄しない。例外は種類と対象を一度記録し、同じ失敗で毎フレームログを増やさない。

### 異常終了とクラッシュ

Renderer ごとの選択時表示は実行中のメモリ上の状態で、Scene にもユーザー設定にも保存されない。クラッシュしても強制終了されても、次の起動には何も持ち越されない。`SessionState` も同時に消える。つまりこの方式では**クラッシュ時の後始末が不要**で、後始末が要るのはドメインリロードとシーン再構築という、プロセスが生きている場面だけになる。

これが第一候補を採る決め手である。永続設定（`showSelectionOutline` と EditorPrefs）を書き換える方式では、抑制中に落ちた瞬間に「OFF のまま、退避値だけが残る」状態が確定し、ツールの後始末コードは一切走れない。復旧は次回起動時の推測に頼るしかなく、その推測が 7 節のとおり原理的に付かない。安定性の差はイベント配線の丁寧さではなく、状態をどこに置くかで決まる。

### リロードと復元の限界

Renderer ごとの通常状態は現行と同じ `Highlight | Wireframe` を基準とする。ただし公開 API にはこの調査範囲で対応する状態取得 API が見つからず、他ツールが以前に指定した個別状態の完全復元は保証できない。併用検証で衝突した場合、双方が毎フレーム上書きし合う運用は避ける。[EditorUtility bindings](https://github.com/Unity-Technologies/UnityCsReference/blob/2022.3/Editor/Mono/EditorUtility.bindings.cs)

ドメインリロードで managed な台帳だけが消え、Renderer 側の状態が残る経路をまず検証する。ここが「残らない」なら SessionState は丸ごと不要になるので、台帳の永続化を実装する前に確認する。残る場合に限り、抑制前に台帳の Instance ID を `SessionState` へ記録し、解除成功後に更新する。新ドメインでは編集を再開せず、台帳の生存 Renderer を解除する。記録失敗時は新規抑制しない（輪郭が出るだけで取り残しは発生しない側へ倒す。ただし理由は一度だけログに残す）。Instance ID は同一 Editor セッションの復旧にだけ使い、再起動をまたぐ EditorPrefs へ保存しない。[SessionState](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SessionState.html)

`SessionState` への書き込みは台帳の内容が変わったときだけ行う。毎フレームの文字列化はしない。

新ドメインで ID を解決するとき、**「今 null」を「破棄済み」と同一視しない**。`InitializeOnLoadMethod` の時点ではシーンがまだ読めていないことがあり、そこで解決に失敗した ID を捨てると、生きている Renderer を Hidden のまま取り残す。解決できない ID は台帳に残し、シーンのロード完了後まで再試行する。回数か時間で上限を切り、諦めるときは対象 ID を一度だけ記録する。managed な参照の null は破棄済みと断定してよいが、ID からの解決結果の null はそうではない、という区別である。

Play Mode 移行でも、解除に失敗した台帳と SessionState を捨てない。Scene Reload を無効にした場合など、Renderer が生存する構成がある。解除成功または managed 参照の破棄を確認したものだけ除去する。同一ドメイン内は managed な台帳を正とし、SessionState はリロードをまたぐ復旧にだけ使う。Instance ID の解決にはオブジェクト再構築との境界があるため、移行時にすべて破棄されると仮定して復旧情報を削除しない。

一方、シーンを閉じる契機では台帳を捨てない。消えるのは閉じたシーンのオブジェクトだけなので、他シーンに残る Renderer の ID を捨てると Hidden のまま取り残す。ID 再利用で他ツールの指定を既定へ戻す損害より、生きている Renderer を取り残す損害のほうが大きい。破棄済みのものは解決不能のまま上限時間で落ちる。

この SessionState は「ユーザーの全体設定の退避」ではなく「触った Renderer の後始末リスト」である。解決結果が Renderer であることを確認する。Renderer 状態が Scene に保存されず再起動で残らないことも採用試験に含める。SessionState は終了時に消えるので、永続設定を変更する方式のクラッシュ復旧には代用できない。

## 6. 公開 API が必要な輪郭に効かない場合

### 安全な既定動作

自動抑制を行わず、編集機能を提供する。必要な場合はユーザーが Gizmos の Selection Outline を変更する。API が例外なく戻ったことを、輪郭が消えた証明として扱わない。実行時に「効かなかったようだ」と判断して内部 API に切り替える仕組みは作らない。

### 自動抑制が必須なら、選択を持たない編集 UI に分離する

専用 EditorWindow に編集対象を保持し、開始時に Unity の選択を空にする。頂点やハンドルは独自のセッションを参照して動作させる。`Selection.gameObjects` を入力にする標準の選択アウトラインは対象を持たなくなる、という公開ソースからの設計上の推論である。NDMF 等が独自に描く強調表示まで消える保証ではない。[HandleUtility の対象収集](https://github.com/Unity-Technologies/UnityCsReference/blob/2022.3/Editor/Mono/HandleUtility.cs)

この方式では CanContinueEditing の選択条件を「ツールが開始時に選択を空にし、その後ユーザーが別の選択をしていない」に変更する。開始時の selectionChanged だけを再入ガードで扱い、ユーザーが別対象を選んだら即終了する。選択を毎フレーム空へ戻してユーザー操作を妨げない。

明示的終了時だけ、選択が依然としてツール管理下で空なら開始時の選択を戻す。ユーザーによる別選択やリロード後には古い選択を強制復元しない。ウィンドウを閉じたら終了する。Inspector、F キーのフレーミング、Hierarchy 強調などの操作変更が必要であり、現在の Inspector 中心の UI を維持する第一候補より変更範囲は大きい。一方、全体設定にも元 Renderer の表示状態にも触れずに済む。

## 7. 旧方式からの移行

新規のグローバル抑制を停止する変更と、既存の退避キーを掃除する処理を分ける。キーの存在だけでは、別 Unity の旧版が編集中なのか、クラッシュの残骸なのか区別できない。新設計でも自動判定できると装わない。

起動時には残存キーと復元メニューを警告で案内し、自動復元・自動削除はしない。別の Unity が旧版で編集中の場合、共有キーを削除すると、その Unity の終了時に必要な復元情報まで失われる。影響は「輪郭が一時的に復活する」だけではない。

旧キーを扱うコードは移行期間限定とする。`Tools/Dennoko Mesh Editor/Restore Legacy Selection Outline` で、旧版で編集中の他の Unity を終了したことを確認して復元する。書き込みと読み返しが成功してからキーを削除し、失敗時は警告してキーを保持する。キーがない OFF 状態はユーザー設定か旧不具合か識別できないので、勝手に ON にしない。

## 8. 採用前の確認

最初にグローバルな `showSelectionOutline` 操作だけを無効化した検証版を作り、Renderer の Hidden だけで消えるか確認する。現行方式を残したままでは有効性を判定できない。通常の Cube、SkinnedMeshRenderer、アバター親選択、NDMF 有効の順に切り分け、親の子 Renderer、元 Renderer、実際に描画するプロキシを区別する。

| ケース | 合格条件 |
| --- | --- |
| 開始・終了を繰り返す | 編集対象だけが抑制され、終了後に通常表示へ戻る |
| 元から Selection Outline が OFF | 開始・終了・リロードでも OFF のまま |
| 編集中にユーザーが Gizmos 設定を変更 | その設定をツールが書き戻さない |
| 複数選択・親選択・別対象への切替 | 選択した階層で必要な輪郭が消える。終了条件は共通判定どおり |
| Scene ビューを閉じて対象変更・削除 | 描画がなくても update でセッション終了と解除が進む |
| プロキシ差し替え・NDMF 一時停止・再開 | 古い生存プロキシに Hidden が残らず、新プロキシも適切に扱う |
| メッシュ後始末・表示解除へ例外を注入 | 他対象の解除は進み、失敗対象の台帳を失わない |
| 開始直後の選択変更・Inspector ロックからの開始 | `Begin` 自身の選択操作でセッションが落ちない。ユーザーが別対象を選んだときだけ終了する |
| スクリプト再コンパイル・上書きインポート | 編集は終了し、SessionState の解除待ちも処理される |
| リロード直後にシーンが未ロード | 未解決の Instance ID を捨てず、ロード完了後に解除まで到達する |
| 対象 Renderer の削除を Undo で戻す | 復活した Renderer に Hidden が残らない。台帳が破棄済みとして落とした分も再評価される |
| Prefab モードの出入り・別シーンを開く | セッションが終了し、解除が完了する |
| 編集中に Unity を強制終了して再起動 | 抑制が残らず、EditorPrefs にも何も残らない |
| Play Mode のドメインリロード ON / OFF | 両方で抑制が残らない |
| Unity 複数起動・再起動 | 別プロジェクトの設定を変えず、非表示状態が保存されない |
| Scene ビュー複数・Inspector ロック・検索表示 | 抑制漏れや解除漏れ、不要なセッション終了がない |
| Unity 2022.3.22f1 と採用対象の Unity 6 | 各バージョンで実際の輪郭とワイヤーを別々に確認 |

集合差分と失敗時の台帳保持は小さな状態テストで確認できる。アウトラインの実描画、NDMF の順序、Scene への非永続性は Unity 上で確認する。採用記録には実機のバージョンと合否を残す。

実装は次の順で切る。

1. 公開 API の有効性確認（グローバル操作を外した検証版）。ここが通らなければ以降は作らず、6 節へ戻る。
2. 共通のセッション判定（`Running` と `CanContinueEditing`）と、解除台帳を持つコントローラー。静的な update 購読もここに含める。
3. ドメインリロードで Renderer 側の状態が残るかの確認。残る場合にだけ SessionState への台帳永続化を足す。残らないなら 5 節の SessionState 関連はすべて不要になる。
4. 旧 EditorPrefs キーの復元専用コード（移行期間限定）。

1 と 2 が通れば、内部 API、グローバル退避、Inspector による復旧を通常経路から取り除ける。
